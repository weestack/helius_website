Measured

Three things that got faster, and by how much

Infrastructure work is easy to describe and hard to verify, so here are numbers instead of adjectives. Each of these was measured before and after, on a production system, by me.

  • 4h → 19min

    Database import time

    Developer environment · Danish e-commerce group

    Restoring a production-sized database locally took four hours, so nobody did it, and the team debugged against data that was weeks stale. I profiled the import path and cut the per-row work the server was repeating, then rebuilt the local setup around the result. Ninety-five per cent faster, and the environment became something people actually used.

  • ~40%

    Faster Nginx rewrites

    Hosting platform · 100+ Linux servers

    Rewrite rules lived in infrastructure-as-code, so every trivial change was an ops ticket and a fleet-wide deploy. I wrote an Nginx extension in Lua on OpenResty that reads the rules from the project itself. Developers commit their own rewrites now, and evaluation is up to 40% faster than the configuration it replaced.

  • 1,500+

    Engineer-hours automated away

    Three years · Hetzner, Google Cloud, AWS

    Across a fleet of more than a hundred dedicated Linux servers: 96 CI pipelines, configuration converged with Puppet and Ansible, and update cycles that used to consume a planned week. Counted from the tasks that stopped needing a person, not estimated from a formula.

Clients are described rather than named. I will name them on request once they have agreed to it, which is not the same thing as putting logos on a page and hoping nobody minds.

Delivery pipeline

What a deploy actually looks like when it is built properly

Seven stages from commit to production. Drag the handle or use the arrow keys to see what happens at each one — and what it costs you when that stage is missing.

Drag, click a stage, or use ← → keys

01

Commit

instant

A push to a branch triggers everything. No manual button, no "remember to also run the deploy job" — the git history is the source of truth for what should be running.

Deploys depend on someone remembering a sequence of steps.

on:
  push:
    branches: [main]
  pull_request:
02

Build

~90s

Reproducible builds with real caching. The same commit produces the same artefact, and the cache keys are derived from lockfiles rather than guessed, so a cache hit is actually correct.

Forty-minute builds that re-download the internet every run.

- uses: actions/cache@v4
  with:
    path: ~/.cargo
    key: cargo-${{ hashFiles('Cargo.lock') }}
03

Test

~3m

Unit and integration tests run in parallel against ephemeral dependencies spun up as services. A failure names the test and prints the relevant log, rather than dumping 2000 lines and letting you search.

A red build nobody can diagnose, so it gets re-run until it passes.

services:
  postgres:
    image: postgres:17-alpine
    options: >-
      --health-cmd pg_isready
04

Scan

~40s

Dependency and image scanning, plus an SBOM generated and attached to the artefact. The gate fails on new high-severity findings, not on the pre-existing backlog — otherwise everyone learns to skip it.

You find out about the CVE from a customer’s security questionnaire.

- uses: aquasecurity/trivy-action@master
  with:
    severity: 'HIGH,CRITICAL'
    ignore-unfixed: true
05

Sign

~10s

The artefact is signed with a keyless workflow identity and pushed to the registry. Production only admits images whose signature it can verify, which makes "how did that get deployed?" an answerable question.

Any image that reaches the registry can reach production.

- run: |
    cosign sign --yes \
      ${REGISTRY}/app@${DIGEST}
06

Deploy

~2m

Progressive rollout with health gates. Traffic shifts a slice at a time, and the rollout aborts itself if error rates move — so a bad release is a non-event rather than an incident.

All-or-nothing deploys, and rollback is a manual scramble.

strategy:
  canary:
    steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - setWeight: 50
07

Observe

continuous

The deploy annotates your dashboards and the alerts know which release they belong to. When something degrades three hours later, the first question — "what changed?" — already has an answer.

Correlating an incident with a release becomes archaeology.

- run: |
    curl -XPOST "$GRAFANA/api/annotations" \
      -d "{\"tags\":[\"deploy\"],\"text\":\"$SHA\"}"

Under the hood

The whole stack, and who owns each layer

This is roughly what I build and operate, from the public edge down to the kernel. Every layer is open-source software running on infrastructure you own. Select a layer to see what goes in it.

Edge

Where traffic arrives. Automatic certificate renewal that nobody has to remember, DNS in code alongside everything else, and caching rules that are reviewed rather than accumulated.

  • Nginx
  • OpenResty
  • HAProxy
  • CoreDNS
  • cert-manager

Ingress & mesh

Routing into the cluster and between services, with mutual TLS by default and traffic-shifting that makes canary deploys possible. Policy lives in version control, not in a console.

  • Traefik
  • Envoy
  • Cilium
  • Gateway API
  • nftables

Orchestration

Where workloads get placed and how they roll out. Sized to your actual load — sometimes a full cluster, sometimes three machines and a load balancer, and I will tell you honestly which one you need.

  • Kubernetes
  • Argo CD
  • Helm
  • Kustomize
  • k3s

Runtime

Your application and the stateful things it depends on. Containers built reproducibly, databases with tested backups, and connection limits set from measured behaviour rather than defaults.

  • containerd
  • MySQL
  • Percona
  • PostgreSQL
  • Redis

Kernel & eBPF

The layer most stacks treat as a black box, which is precisely the problem. eBPF lets you watch process and syscall activity from inside the kernel without a proprietary agent, and LSM and kprobe hooks let you cut attack surface at the source rather than filtering after the fact. This is where I spend most of my time.

  • eBPF
  • aya
  • bpftrace
  • LSM
  • kprobe
  • nftables
  • SELinux

Telemetry

Everything above emits here, and this is what you actually look at during an incident. Correlated signals, alerts tied to user-visible symptoms, and retention tuned so the bill stays predictable.

  • Zabbix
  • Prometheus
  • Grafana
  • Loki
  • OpenTelemetry
  • Alertmanager

My pledge

I deliver, you own 100%

This is the part of the site I would most like to be judged on. Each of these is a specific, checkable commitment rather than a value statement — if I break one, you can point at it.

  1. 01

    Everything in your repository

    Pipelines, manifests, Terraform, dashboards, alert rules, runbooks. Committed to repositories you own, under a licence you pick. Nothing lives only on my machine or in an account I control.

  2. 02

    Open-source components only

    Every tool I put into production is open source and self-hostable. Where a managed service genuinely is the right answer, I say so and you decide — but the default is software you can read.

  3. 03

    No metering, no seats, no hosts

    I charge for days worked. Nothing I build bills you for growing, and there is no component that phones home to Helius or counts your servers.

  4. 04

    Handover is included

    Documented architecture with the reasoning, runbooks per alert, and a working session where your team drives. Not an upsell, not a final invoice line.

  5. 05

    The exit clause

    Stop the engagement whenever. No notice designed to trap you, no exit fee, no migration project. Everything keeps running because none of it needed me to keep running.

  6. 06

    Upstream where it helps

    Fixes and tooling that are generally useful go back to the projects they came from, or get released standalone — with your permission, and never containing anything of yours.

Frequently asked

The questions people actually ask

Including the awkward ones about price and how to get rid of me.

How do engagements usually work?

Most start with a paid scoping conversation — a couple of hours where I look at what you have and tell you what I would do. After that it is either a fixed-scope project with a defined deliverable, or a retainer for a set number of days a month. I do not do open-ended time-and-materials without a scope; it is bad for both of us.

Who owns the code and configuration you write?

You do, entirely. Everything lands in your repositories under a licence you choose. There is no Helius-branded agent, no proprietary control plane, no component that stops working if you stop paying me. If a piece of it is generally useful I may ask to open-source it separately — but that is a request, never a condition.

Why only open-source tooling?

Because I have been on the wrong end of the alternative. Closed agents you cannot audit, per-host pricing that punishes you for growing, and vendors who change the licence once you are committed. Open-source components mean you can read what runs on your servers, host it yourself, and replace me without replacing your stack.

Do you take on-call or 24/7 support?

Not as a primary on-call rotation — I am one person, and pretending otherwise would be dishonest. What I do is build the alerting and runbooks so your team can hold the pager competently, and act as an escalation contact during agreed hours on a retainer.

What access do you need, and what happens to it afterwards?

The least that lets me do the work — usually a named account with scoped permissions, never a shared root credential. Access is revoked at the end of the engagement and I will remind you if you forget. I do not copy production data to my machine; if I need realistic data for testing we generate or anonymise it.

Can you work with our existing team and tools?

Yes, and that is usually the point. I am not interested in replacing a working setup for the sake of my preferences. If you already run GitLab, or Nomad instead of Kubernetes, or a managed database, we work with it. I will tell you plainly if I think something is a genuine liability, and then it is your call.

What does it cost?

Day rate, quoted per engagement once I know the scope, and it is on the invoice rather than buried in a platform subscription. Scoping conversations are billed at the same rate. Email me with a rough description and I will give you a number and a range for how many days I think it takes.

How do we end it?

You say so. There is no notice period designed to trap you and no exit fee. Handover is part of every engagement rather than an upsell: documented architecture, runbooks, and a session where your team drives while I answer questions. The test is whether everything still runs a month after I stop — and it does, because none of it depends on me.

Tell me what is broken

A paragraph about what hurts is enough to start. I will reply with what I think it actually is, roughly how long it takes, and whether you need me at all — that last answer is sometimes no, and I would rather say it early.
